## 7.1 团队能力画像：一支"验证派"团队

## 7.2 分工原则与已交付物对照

**最新决策：分工不再按"章节/模块绑定到人"，整个项目共同推进。**
《团队讨论记录》第 23 节曾给出按学科切分的初版分工，但团队随后明确放弃了
这一做法：不按"谁写第几章、谁做哪个模块"切蛋糕，而是所有成员围绕同一条
pipeline 共同推进，个人的能力画像（7.1）用于判断"谁来把关哪类问题"，而不是
"谁独占哪块产出"。因此本节以**实际合并进 main 分支的 GitHub PR 记录**为准
对照成果，凡 SYNC_LOG 未明确署名者，一律如实标注为团队共同交付，不做虚构归属。

## 7.3 协作工作流：AI 辅助协作本身就是参赛亮点

团队的日常工作流是一条"AI 规划—人工把关—AI 执行—可追溯合并"的闭环，
并全程以 GitHub 实时共享进度：

1. **规划设计（K3）**：由 K3 基于 TODO 与讨论记录设计实施方案与任务切分，
   明确每步的验收标准（如"测试通过数""回填字段齐全"）。
2. **人工确认**：方案经团队人工审阅、调整后才进入执行；涉及口径与系数的判断
   （如 ontology 弹性系数、财务模型假设）明确留待经济金融成员把关，AI 不擅自定夺。
3. **执行（K2.7）**：由 K2.7 按确认后的方案在独立 feature 分支上实现代码与文档，遵循"每个 PR 只含自己的 diff"的小步堆叠原则（PR #5–#8 即四个按序合并的堆叠 PR）。
4. **PR 合并与留痕**：合并前必须通过全量测试（当前 140 passed）；每次推送后在
   `SYNC_LOG.md` 表首追加一行同步记录，写明变更文件、验证结果与遗留事项，
   团队任何人可随时回看"哪些传过了、新增了啥"。

这条工作流已经受过真实考验：main 分支曾意外回退至 PR #5 合并点，导致 #6–#8 内容丢失（PR 状态仍显示 MERGED）；正是靠 SYNC_LOG 的完整留痕与 PR 记录，团队得以用 PR #10 精确定位 #8 合并点（24ad46e）并整体恢复，恢复后当时全量测试为 129 passed，后续 PR #18–#26 已扩展至 140 passed。此外，PR #11 的证据回填硬性要求"核验人字段为空即拒绝写入"，把"AI 辅助但不替代人工核验"的原则写进了代码门控。

对一支以"证据与验证"为母题的团队而言，这套工作流不是后勤细节，而是产品的
预演：**正如同 Claim2Value 要求每一条 claim 经核验后方可写回证据库，团队也
要求每一项产出经测试与人工确认后方可合并进 main。**"我们怎样协作"与"我们
让 Agent 怎样工作"，在方法论的层面上是同一个东西。
